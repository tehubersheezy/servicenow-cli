# Authentication: OAuth / SSO, API key, external token

## Modules

- `src/oauth.rs` → OAuth 2.0 for SSO: PKCE, loopback or pasted-code login, token exchange (authorization_code/refresh/client_credentials/jwt_bearer), ensure_access_token()
- `src/jwt.rs` → the jwt_bearer grant's signed assertion: PEM key loading (PKCS#8 RSA/EC, PKCS#1 RSA) + RS256/384/512 and ES256/384 signing on `ring` directly (already linked by rustls — no JWT crate)
- `src/external_token.rs` → `auth = "token"`: static token or `token_command` (run via the shell, stdout = token or JSON), cache-only-with-stated-expiry contract
- `src/cli/auth.rs` → session/identity core behind `sn profile login/logout/status/refresh` (no clap surface of its own; login runs the flow for a configured oauth profile, no config mutation) + whoami (authenticated-identity read, shared with profile.rs)

A profile authenticates via `auth = "basic"` (default), `auth = "oauth"`, `auth = "apikey"`, or `auth = "token"` in its `config.toml` entry. OAuth serves SSO-fronted instances (Okta/Azure AD/ADFS) where the password lives in the IdP, so Basic and the password grant can't work. `apikey` stores the platform's inbound REST API key in `credentials.toml` and sends it as the `x-sn-apikey` header (`Auth::ApiKey` in `client.rs`, marked sensitive so reqwest redacts it); it verifies through `whoami` like Basic, and switching a profile between methods clears the abandoned method's secrets.

- **Split by secrecy:** non-secret OAuth config (client_id, redirect_uri, endpoint overrides, grant, pkce) lives in `config.toml` under `[profiles.<name>.oauth]`; the client secret and cached tokens live in `credentials.toml` (0600), mirroring the username/password split.
- **Three grants:** `authorization_code` uses interactive browser login with PKCE S256; `client_credentials` is headless and requires a client ID and secret; `jwt_bearer` is headless too (see below). A dedicated public client uses `http://localhost:8400/callback` by default, registered exactly in Application Registry. Confidential authorization-code clients can supply a secret explicitly. **With no `--client-id`, `authorization_code` defaults to the ServiceNow SDK's public client** (`config::SDK_OAUTH_CLIENT_ID` = `543e5655f77746a28228c6009a599dfb`, the `oauth_entity` "ServiceNow SDK" — now-sdk's own `DEFAULT_SDK_OAUTH_APP_CLIENT_ID`). Its only registered redirect is the instance-relative `/sdk-oauth.do`, which renders the code for the user to paste, so `default_redirect_uri_for(client_id)` keys the redirect default on the client, and `oauth::is_instance_redirect` (a leading `/`) swaps the loopback listener for a terminal paste prompt (refused on a non-TTY; PKCE, not `state`, binds the pasted code to the login). Verified live on dev421992. The SDK client is borrowed, not ours, so every profile landing on it reports `SDK_CLIENT_ADVISORY` — a `warning` key in `profile add`'s JSON, a stderr line from `init` — advising a self-registered client. `client_credentials` and `jwt_bearer` have no default (the SDK client is public: no secret, no JWT verifier map).
- **`jwt_bearer` (RFC 7523)** posts `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer` + `assertion` (+ `client_id`, + `client_secret` when stored) to `/oauth_token.do`. The assertion (`jwt.rs`) is `iss`=`aud`=client_id, `sub`=`jwt_subject` (matched against the endpoint's User field), `iat`, `exp` = +300s, a random `jti` (JTI verification is on by default, so a replay is refused), and `kid` in the header when set. `config.toml`'s `[oauth]` holds `jwt_key_file` (made absolute at add time), `jwt_subject`, `jwt_kid`, `jwt_alg` — a path, never the key. Measured 2026-09-28 on dev421992 against an `oauth_jwt` record + `jwt_verifier_map` + `sys_certificate`: RS256, RS512 and ES256 all mint; `kid` is optional when the endpoint has one verifier map; a confidential client without its secret is a 401; an unmatched `sub` is 400 `invalid_grant`. **No refresh token is issued**, so `ensure_access_token` re-mints from a fresh assertion when the cache goes stale (`OAuthGrant::is_headless`, shared with client_credentials). The key is loaded at `profile add` time even under `--no-verify`, so a bad path or encrypted key fails before anything is written.
- **Endpoints:** authorization `GET /oauth_auth.do`, token `POST /oauth_token.do` (overridable per profile).
- **Commands:** `sn profile login` (pure session command, no flags: resolves the selected profile, requires `auth = "oauth"` with an `[oauth]` block — a basic profile errors `does not use oauth; run \`sn init\`` — runs the flow with the stored grant, caches tokens), plus `sn profile status`/`refresh`/`logout`. All emit success JSON to **stdout**; OAuth profiles are configured via `sn init --auth oauth` or `sn profile add --auth oauth`.
- **Headless setup:** `client_credentials` mints a token without a browser, so `sn profile add` verifies it like any other credential. `authorization_code` cannot be verified without one — `sn profile add` refuses on a non-TTY rather than persist an untested profile, and points at `--no-verify` + `sn profile login`.

- **Transparent refresh:** `build_client` (in `cli/kernel.rs`) calls `oauth::ensure_access_token` when constructing a client for OAuth profiles — returns a cached token, refreshes a stale one via the refresh token (or mints a fresh one for client_credentials/jwt_bearer), persists new tokens. Call sites need no changes; the `Client` is auth-agnostic (one `Auth` enum `Basic`/`Bearer`/`ApiKey`/`Session`/`None`, applied in `send()`).
- **External bearer token (`auth = "token"`)** — for tokens something else issues (an IdP minting ServiceNow-audience tokens, Vault, a cloud CLI). Either a static `token` in `credentials.toml`, or `token_command` in `config.toml` (a command wins if a hand-edited file has both). `external_token::ensure_token` runs the command through `sh -c` / `cmd /C` with stdin closed and `SN_PROFILE`/`SN_INSTANCE` in its env, bounded by `--timeout` (default 30s). Stdout is the bare token or JSON (`access_token`|`accessToken`|`token`; expiry from `expires_at`|`expires_on`|`expiresAt` — ms detected by magnitude — else `expires_in`). **The cache contract:** the result goes to `credentials.toml`'s `token_cache` only when the command stated an expiry, reused until 60s before it; no stated expiry means the command runs on every invocation (a guessed lifetime would keep presenting a token the issuer may have revoked, and an agent can't tell that 401 from a missing role). `sn profile refresh` re-runs it; `logout` drops `token_cache` along with `oauth_tokens`. Output is a secret: never logged, never quoted in an error (errors quote only a stderr tail), never on a child's argv. Command failures (spawn, non-zero exit, timeout, unparseable output) are `Error::Config`, exit 1 — deliberately not `Error::Auth`, which would publish a `status_code` no HTTP exchange produced. Unlike OAuth refresh, a fetch holds **no** config lock across the command: single-flight exists there because refresh-token rotation makes a duplicate fatal, which a command has no analogue of, and holding the lock across an arbitrary user command would park every other invocation. Verified live with a JSON-with-expiry command (ran once, then served from cache), a bare-token command (ran every call), a static token, and `sn watch` (bearer-minted cookies are accepted by AMB).
- **Mechanism-specific flags are refused under another mechanism** (`--token*` without `--auth token`, `--jwt-*` without `--grant jwt_bearer`), exit 1 naming the right flag — silently dropping `--jwt-key-file` would otherwise leave an authorization_code profile and a browser refusal that never mentions it. Rewriting an OAuth profile also clears its cached `oauth_tokens`: tokens minted under the old client/grant/subject must not answer for the new one.
