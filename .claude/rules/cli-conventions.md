# CLI conventions (every command module)

## Modules

- `src/cli/mod.rs` → Cli struct, GlobalFlags, all top-level command registration; command-specific arg structs live in their modules
- `src/cli/kernel.rs` → the shared command kernel: connect()/emit(), build_profile/build_client/build_client_with_headers, write_response/unwrap_or_raw/take_field/bool_opt, confirm_destructive/confirm_delete, SessionScope (the `sn impersonate` client override)
- `src/cli/args.rs` → shared clap arg vocabulary, flattened into the command modules' arg structs: BodyArgs (--data/--field), WaitArgs (--wait/--wait-timeout), DisplayValueOpt, SetLimit/Paging (const-generic per-site defaults), DisplayValueArg. Flatten position is help order; a site whose help text differs keeps its own declaration

- Exposed Table API `sysparm_*` parameters have friendly flags (e.g. `--query`) and a raw alias (`--sysparm-query`) mapping to the same field, via clap's `alias` attributes in the command modules and `cli/args.rs`.
- `table update` and `cmdb update` use PATCH for existing records. `replace` (PUT) was removed in 0.11.0: measured on a live instance, PUT and PATCH left a record byte-identical, because ServiceNow treats both as partial updates — PUT does not blank omitted fields. Clear a field by setting it explicitly. Don't reintroduce a PUT verb without re-measuring; the redundancy is a ServiceNow behavior, not a CLI choice.
- **`--display-value` defaults to `true`** on `table`, `get`, `gr`, `change`, `aggregate`, `scores` (`watch` has no such flag — an event's `record` already carries `{display_value, value}` pairs). This also localizes dates into the caller's timezone/locale, and such a date will not round-trip into an encoded query — use `--display-value false` when a value has to be fed back to the API.
- **Help is organized in three tiers, and every arg carries a doc comment.** `GlobalFlags` has `next_help_heading = "Global options"` so the 11 propagated globals don't zipper through each command's own flags (clap gives every `Args` container its own display-order counter and merges them). Raw `sysparm_*` passthroughs nobody reaches for get `help_heading = ADVANCED` (the const in `cli/mod.rs`); the default "Options" section is left as the working set, in declaration order — so **declare fields in order of usefulness**. A new arg without a `///` doc comment is a bug: `sn introspect` is the audit (`args[].help` must be non-null for all of them).
- `cli::command()` wraps `Cli::command()` to rewrite every usage line as `sn <path> <POSITIONALS> [OPTIONS]`; `cli::parse()` is what `main.rs` calls, so errors and `--help` agree. Anything building the command tree (`completion.rs`) must go through `cli::command()`, not `Cli::command()`, or its usage lines will disagree.

- **Typed destructive commands are gated by `cli::kernel::confirm_destructive(yes, verb, what)`** (`confirm_delete` is the `delete`-verb shim `attachment`/`cmdb` still call). On a TTY it prompts `<Verb> <what>? [y/N]:` on stderr; with a non-terminal stdin it refuses with ``"<verb> <target> requires --yes when stdin is not a terminal"``.
  - **The verb must be the one the caller typed.** The guard's prompt used to be a hardcoded "Delete {what}?", which fits only a row deletion — which is why `catalog cart-empty`, `catalog cart-remove`, `change conflict remove` and `profile remove` shipped with no gate at all, having nowhere to plug in. `catalog cart-remove` and `change conflict remove` say "remove", not "delete", a word in neither caller's argv. Give a command its own args struct rather than reusing a shared one when the sibling uses are reads (`ChangeSysIdArg` is shared with `nextstates`/`schedule`/`ci list`/`conflict get`, and a `--yes` on a read reads as if the read were dangerous).
  - **`sn raw` is an unguarded passthrough**, including DELETE; it has no `--yes` flag.
  - **Gate before `build_profile`/`build_client`.** The check reads nothing but argv, and running it after authentication hands a pure argv mistake to the IdP: on an OAuth profile `build_client` mints a token first, so an unreachable instance answers with exit 3 and a token-endpoint URL while the exit-1 usage error never prints.
  - `updateset back-out` and `app rollback` are gated too. Both are recoverable in principle and a human types them deliberately, but this CLI's audience is LLM agents and both are the shape an agent fires by accident: one flag, instance-wide effect, asynchronous, no second confirmation downstream. `--yes` is one token in a script; an unintended back-out is a recovery project.

- The shared `pub(crate)` command kernel lives in `cli/kernel.rs`: `connect(global)` (the `build_profile` → `build_client` preamble; keep the two-step form only when the handler reads the resolved profile itself — `open`, `watch`, the OAuth flows, `ping`, and the `build_client_with_headers` callers `raw`/`api`; `connect_without_redirects` is the same preamble for a client that must see a `3xx` itself — `script`), `emit(global, resp)` (`unwrap_or_raw` → `write_response`, taking `resp` by value so the envelope is moved, not cloned), plus `bool_opt`, `take_field` and `confirm_destructive`/`confirm_delete`. `format_from_flags` is **private** on purpose — it plus `emit_value` was the bypass that let `aggregate`, `scores list`, `scores favorite` and `open` accept `--output table` and ignore it, so the bypass is now a compile error rather than a convention. Nothing is re-exported through `cli::table`, so the old import path cannot come back one convenient `use` at a time.
- JSON responses go through `cli::kernel::write_response(global, &value)` (usually via `emit`), which routes to `output::write_value` (JSON, default/raw) or `output_table::write_table` (`--output table`). `unwrap_or_raw` treats `Table` like `Default` (envelope unwrapped, then rendered).
