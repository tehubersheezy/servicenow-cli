# Claude Code plugin: skill and `sn` panel

This repo is also a Claude Code plugin and its own marketplace (`.claude-plugin/plugin.json` + `marketplace.json` + `skills/sn/`). The skill is a directory — `SKILL.md` plus `references/{shapes-queries,change,watch,cicd}.md` — loaded progressively: `SKILL.md` is always in context when the skill fires, the references only when it points at one. `.claude/skills/sn/` is the in-repo copy (`/sn`); `skills/sn/` is for external distribution and is **identical except for the `allowed-tools: Bash(sn *)` line**, which declares CLI access for installed users, subject to host permissions. Keep all ten files in sync; `diff -r` the two trees.

**The skill documents what `--help` cannot, and nothing else.** Measured against a no-skill baseline across ten A/B runs, an agent with only the CLI matched an agent with the old 1,041-line skill on every task, because this CLI's help and its self-naming errors already teach the flags (`sn cmdb create --help` carries the IRE envelope, the Java String cast *and* the `source` ambiguity). What a skill can add is the *instance's* behavior, which no help text can reach: response shapes (`change` wrapping every field, `cmdb` nesting under `.attributes`, the `__meta` element, aggregate's sibling `groupby_fields`), silently dropped query terms, exit 4 meaning a missing role rather than a bad credential, and the CICD status contract. When adding to the skill, the test is: *can the binary teach this at the moment of need?* If yes — help text, a self-naming error, or validation the CLI already performs — leave it out.

**The `sn` panel** (`hooks/`, Claude Code function hooks — an early-access API that may move between Claude Code releases). Every `sn …` Bash call, and every load of the `sn` skill (`skill.prompt` for `sn` or `<plugin>:sn`), lands an entry and brings the pane up again, even after it was closed. `parse.ts` picks out the first `sn …` in a shell command (a quote-aware split on `;`/`&&`/`||`/`|`/`(`/`` ` ``, where `2>&1` is a redirection rather than a separator) and sorts argv the way clap reads it, driven by **`catalog.ts`, generated from `sn introspect`** by `tests/plugin_catalog.rs`: the subcommand tree, each command's positional names, and which long/short flags consume the next word (a flag in front of an implied verb is checked against its whole subtree). That test fails when the catalog drifts, so a new command or flag is one `UPDATE_PLUGIN_CATALOG=1 cargo test --test plugin_catalog` away from being parsed right; nothing in the hooks is hand-kept per flag. Implied verbs on `table`/`cmdb` are resolved as `cli::parse` does. Positionals named `table`/`class`/`staging_table` (or a `table:ref` `reference`) are the call's table; `sys_id`/`task_sys_id`/`record` its record.

`kinds.ts` classifies each command into a **kind** — read, write, delete, run, stream, session, skill — which sets its glyph and color, its running text, how its summary reads, and its filter chip (hotkeys 1–7). The leaf verb decides by default (`create`/`update`/`set`/`add` write, `delete`/`remove` delete, `run`/`trigger`/`launch` run, `tail` streams), so only a command whose verb says nothing needs a `BY_COMMAND` line (`BY_GROUP` makes all of `context`, `profile` and `set` session); `sn raw` is its method's kind and `sn graphql` a write only for a `mutation`. `outcome.ts` summarizes what a call printed: reads name what came back rather than count lines — the record count plus the first three records' labels (an array or JSONL; a `get` is one record even when `-f` drops `sys_id`; cmdb's `.attributes` is looked into), an object's scalars one level deep (`count=44`), text its first line (a help page's about); shell redirections (`2>&1`, `> out.json`) are dropped before parsing, so they are neither shown nor read as an operand, writes and deletes lead with their past tense and the record, streams count events, and a failure shows its exit code's meaning plus the stderr envelope's message. A command with a shape of its own gets a `SUMMARIZERS` entry (`script run`: `completed · <first logged line>`, or on failure the error's type, line and message). **Each entry draws through a component in `views.tsx`** (`h` takes function components; they get the surface's element table as `ui`, and keep no state — what they read, like which entries are expanded, is an atom the pane passes down): `ENTRY_VIEWS` maps a command to its own component, everything else is `RunEntry`. `ScriptRunEntry` folds the script (numbered) and its output (logged lines, then `· messages`) and has no Open or Output button: its header and summary rows are plain Buttons that toggle it, since only a Button takes a press and a Button is one line of text (no clickable Box). The script is captured as the call runs: inline from argv (and left out of the args line), a heredoc from the command text, `@file` read from the session cwd before it runs, and `@-` fed by a pipe copied by a second tee in front of sn (`stdinPipeAt`) to `<id>.js` beside the output. Each call carries an **Open** button that runs `sn open` through `$.process.run` with the call's own profile: `LIST_VIEW` commands open their list view with the same `-q` (needs sn ≥ 0.14.0), `RECORD_FORM` commands their record as `table:<sys_id>` (the sys_id from the output when it held one record, else the one the command named), `FORM_TABLE` commands a record in a table they do not name (`change get` → `change_request`, `script run` → its `sys_script_execution_history` row, failed runs included). A delete or a failure gets no button, nor does a call whose table, query or profile the shell filled in (`-q "$Q"`, `$(…)`): the hook sees the command's text, not its expansion. **What every call printed is saved, outside the model's context,** to `sn-panel/outputs/<tool_use_id>.out` in the Claude Code config dir, behind each entry's **Output** button (`code`, else `open -t`). An unpiped call's file is written from the tool result the hook already holds. A piped call's is not visible to the hook, so the hook rewrites the command beneath the model with `| tee <file>` between sn and its `|` (`parse.ts::teeCommand`, at `pipeAt`; never for `|&`, `||` or a background call): the pipeline's output and exit status are unchanged, the model sees only what the pipeline printed, and the entry is summarized from the copy — records counted, Open offered — with sn's own failure read from the error envelope, since the pipeline's exit status is its last command's. Files leave with their entries (evicted past 50, or Clear) and any older than 7 days at session start. The panel's own failures (an Open that `sn open` refused or that could not start, bookkeeping that threw) go to `sn-panel.log` in the Claude Code config dir (`~/.claude/`, or `CLAUDE_CONFIG_DIR`) as JSONL, last 200 kept, and to the debug log; a failed Open records its argv, the whole stderr, `sn --version` and `PATH`, because the usual cause is a different `sn` answering than the one the shell finds. `/sn-panel` opens the pane by hand (below 144 columns an unasked pane waits, so the command is the way in). State lives in `$.state` keyed by the plugin's **name**, so renaming the plugin means renaming the keys and the `PluginState` entry in `types/index.d.ts`; state outlives a reload, so a field added to an entry is optional (older entries lack it) and a changed one renames the key. `claude plugin test .` runs `hooks/panel.test.ts` (in `hooks/`, because `tests/` is Cargo's); `claude plugin validate .claude-plugin/plugin.json` checks the module — validate on `.` reads only the marketplace manifest. The engine lays `.claude-plugin/types/` (self-gitignored) when it loads the plugin from disk, which is what the root `tsconfig.json` extends.
