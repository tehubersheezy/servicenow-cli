# `sn appmanager`

## Modules

- `src/cli/app_manager.rs` → sn appmanager list/search/show/install (Application Manager: installed, updatable and available store apps and plugins in one row shape; whole-list fetch with client-side search, sort and paging; `show` resolves a scope, plugin id or app sys_id and checks the record returned is the one asked for; `install` activates one resolved, not-yet-installed plugin behind `--yes` and hands the tail to `progress::finish_cicd`). `src/cli/app.rs` is the unrelated `sn cicd app` (App Repository over the CI/CD API).

**Endpoints**: `POST /api/sn_appclient/appmanager/apps?tab_context=`; `POST …/plugins?tab_context=`; `GET …/app/{sys_id}`; `GET …/plugin/{id}`; `GET …/plugin/activate?plugin_id=&load_demo_data=`

The scripted REST API behind the Application Manager UI ("AppManager(Internal API)", also at `/v1/appmanager`). Undocumented in the product docs. Measured on dev457896 (Brazil) as admin, 2026-11-16, and read from its script includes (`AppInfoService`, `PluginInfoHelper`, `AppManagerApiUtil`, `AppManagerHandler`). Only admin is in scope for this verb; it is not tested as `itil`.

- `tab_context` (`installed` | `updates` | `available_for_you`) is mandatory on both list routes (400 without). The body is a filter object; the CLI sends `{}`. Apps answer `result.apps`, plugins a bare `result` array — both canaried (`Error::Instance`).
- **Never page or search these routes.** The plugin route removes plugins that are store apps by comparing against the same request's apps query, which obeys the same `sysparm_limit`: paged at 200 it returned 963 rows for 961 plugins (one leaked, one repeated). `/apps` `search_key` is a Zing text search (`flow` → "Docker Spoke", `ir_query_score` 50), the plugin route's is a regex contains — different semantics per kind. Totals come only in an `x-total-count` header. Whole lists: 252 apps (122 KB, ~1.0 s) + 961 plugins (470 KB, ~1.5 s); 455 available plugins (246 KB, ~0.5 s).
- List rows: apps carry `version`, `latest_version`, `update_available` (`"0"`/`"1"`), `vendor` (null or a name); plugins carry `app_id`, `app_name`, `active` (`"0"`/`"1"`), no version, and a `sys_id` that is the plugin id again. Plugin `update_available` exists only for a customized plugin whose `sys_app_customization.version` trails.
- `GET /app/{id}` takes a sys_id only (a scope is 400 "No app found matching sourceAppId"), so scopes resolve through the lists, installed then available. It mints tiny-URL rows per call (~1 s). `version` and `versions` (empty for installed apps) are in the detail; `dependencies` is one `id:version,…` string (`sys` for platform plugins).
- `GET /plugin/{id}` answers an unknown id with 200 `{"plugin":{}}`, is case-sensitive, and returns `{}` for a store app's scope. Zero plugin ids equalled an app scope across 1,668 rows, but the namespace is shared, so with no `--kind` both sides are asked and a double answer is exit 1.
- **The write routes are GETs** (`/app/install|update|repair`, `/plugin/activate|repair|rollback`, plus `/sync_apps`, `/loadDemoData`). `ROUTE_WORDS` are refused as ids before the network; extend it with any new fixed segment under `/app/` or `/plugin/`. Only `/plugin/activate` is wired (`sn appmanager install`); **store-app install and update are out by decision** (2026-11-16: the store is not relevant, and dev457896 cannot reach it). Activation measured twice on dev457896 (`com.sn_signature_pad`, `com.sn_casetypes_selector`): 200 with `status:"0"` Pending and `links.progress.id`, terminal `status:"2"` "Plugin activated/upgraded successfuly" after 35–45 s, `can_rollback` true afterwards. `load_demo_data=true` is read from the handler script, not measured. `install` gates on `--yes` (an activated plugin cannot be deactivated; `sn cicd app install` stays ungated because an app-repo install can be rolled back), refuses an installed plugin (exit 1), never sends an id `GET /plugin/{id}` did not return, treats in-band `status` `"3"`/`"4"` as `Error::Api` with `NO_HTTP_STATUS`, and treats an answer with no `links.progress.id` as `Error::Instance`. Also measured: `GET /app/install` with a nonexistent `app_id` is **accepted** — 200, `status:"0"` Pending, `links.progress` pointing at `/api/sn_cicd/progress/{id}` (so `sn cicd progress` and `finish_cicd` read it; `/appmanager/progress/{id}` returns the same tracker as `{name,state,message,percent_complete,results}`) — and then sits "Attempting retry" in the Application Operation Queue until cancelled (tracker `state=4`) or the 48 h timeout. So an id must be resolved before any write is sent. `GET /plugin/activate` with an unknown `plugin_id` refuses in band: 200, `status:"3"`, `error:"Plugin ID is not valid"`, no `links`. `GET /sync_apps?request_type=trigger_apps_sync` returns `{trackerId}`; `request_type=get_apps_sync_status&tracker_id=` reports `{isComplete, errorMessage}`. **dev457896 cannot reach the store** ("Access to store has been restricted due to invalid credentials"), so it has no available store apps and no updates: store-app install and update cannot be measured on it.
- `available_for_you` queues the event `sn_appclient.update_last_installed_from` per call (as the UI does). The available-app row shape is unmeasured (see the store note above).
- One REST_Endpoint ACL ("App Manager Security Rules") guards every route: `admin`, `sn_appclient.app_client_user`, `sn_appclient.app_client_company_installer`, or `unified_plugin_read_only`. Others get 403 "User Not Authorized", which `explain` extends with the roles (still exit 4). A missing route is the usual 400 "Requested URI does not represent any resource", rewritten.
- `--output raw` needs `--kind` (one request, one envelope) and refuses `--limit`/`--offset`; under `search` it is the unfiltered envelope, as `sn api search`.
