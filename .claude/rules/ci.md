# CI/CD workflows

- `ci.yml` — fmt + clippy + test on ubuntu/macos/windows (PRs + pushes to main).
- `security.yml` — `cargo audit` (RustSec) + `cargo deny check all` (license/source/banned-crate policy in `deny.toml`); on dep changes + daily 06:00 UTC.
- `lockfile-refresh.yml` — weekly (Mon 05:00 UTC) + manual `cargo update`; force-pushes a rolling `bot/lockfile-refresh` branch, opens/updates its PR, then **approves the PR's own parked runs**. Three measured facts carry the design: `pull_request` runs for a `GITHUB_TOKEN`-created PR fire but park as `action_required` (jobless, context-less; kin to the suppression that kills attach-provenance's release trigger); rulesets evaluate **PR-associated check suites, not commit check runs**, so dispatching CI at the branch greens the SHA while the merge stays "base branch policy prohibits the merge" — approval of the parked runs is the only unblock; and `GITHUB_TOKEN` *may* approve the runs its own PR parked, given `actions: write` plus the repo setting "Allow GitHub Actions to create and approve pull requests" (enabled 2026-08-31, `default_workflow_permissions` still `read`; without it `gh pr create` fails even with `pull-requests: write`). Bot PR #98 proved the PR reaches CLEAN with no human, but CLEAN isn't merged: until 2026-10-20 a human still had to merge, so Security stayed red 09-15→21 and 10-01→20 (#105 sat green for three weeks). The last step now runs `gh pr merge --auto --squash` (repo "Allow auto-merge" enabled 2026-10-20); a `GITHUB_TOKEN` merge fires no push workflows, so the next daily Security run is the first check of the merged lockfile. Exists because Dependabot reaches neither lockfile-only transitive deps nor yanks (not advisories) — a yanked crate otherwise leaves the daily Security run red until a human runs `cargo update` (chacha20 0.10.1, 2026-08-28). A red Security run midweek: `gh workflow run lockfile-refresh.yml`.
- `scorecard.yml` — OSSF Scorecard; weekly + push to main; publishes to scorecard.dev.
- `release.yml` — cargo-dist on `v*` tag: builds {x86_64,aarch64}-{linux,macos,windows}, shell/PowerShell/MSI installers, Homebrew formula, and signed provenance attestations (`gh attestation verify`); auto-publishes the formula to `tehubersheezy/homebrew-sn` via `HOMEBREW_TAP_TOKEN`.
- `release-guard.yml` — hooks `Release` via `workflow_run`, so it still runs when every job inside skipped. Fails if any release job was **skipped**, if the tag published fewer than 20 assets, or if the Homebrew formula version doesn't match the tag. Exists because a green `Release` does *not* mean anything shipped (see below).
- `mask-check.yml` — **run before tagging** (`gh workflow run mask-check.yml`). Preflight that pushes the top CHANGELOG section through a job output, the exact path that breaks, and names the offending line if it would be withheld.
- CodeQL runs via GitHub's **default setup** (rust + actions, PRs + pushes + weekly) — deliberately no codeql.yml: default setup rejects SARIF from advanced-setup workflows, so a workflow file here can never upload.
- `fuzz.yml` — cargo-fuzz (nightly), weekly + on PRs touching `fuzz/`; five bounded minutes per target. The `fuzz/` crate has its own `[workspace]` so tests/clippy/dist never build it; `record_ref`'s parse fns are `pub` solely for it.
- `attach-provenance.yml` — pulls each asset's attestation bundle from the store and uploads the DSSE envelopes as `sn-<tag>-provenance.intoto.jsonl`. **Run it manually after every release**: `gh workflow run attach-provenance.yml -f tag=<tag>`. Its `release: published` trigger never fires — release.yml publishes with its own `GITHUB_TOKEN`, whose events GitHub suppresses (measured: zero runs across v0.13.0/v0.13.1; both needed the manual step). A separate workflow on purpose: release.yml is dist-generated and `dist generate` would drop an added step. Scanners (Scorecard's Signed-Releases) only read release *assets*; `gh attestation verify` reads the store — this serves both.
- Config: `dist-workspace.toml` (cargo-dist), `wix/main.wxs` (MSI template; stable GUIDs in `[package.metadata.wix]` of `Cargo.toml`), `.github/dependabot.yml` (weekly grouped dep PRs for cargo + github-actions).
- **Actions are pinned by commit SHA** (with a `# vX.Y.Z` trailing comment Dependabot keeps current). `release.yml` is hand-edited on top of the dist output — SHA pins, job-scoped token permissions (top-level `contents: read`, write only on `plan`/`host`), and hash-verified installer downloads instead of `curl | sh` — under `allow-dirty = ["ci"]` in `dist-workspace.toml`. **A future `dist generate` reverts all of it**; re-apply (the diff is small and self-describing) before tagging. `dtolnay/rust-toolchain` pinned by SHA no longer reads the toolchain off the ref name, so every use passes `toolchain:` explicitly.
